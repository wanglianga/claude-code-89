# 绿衣循环 · 社区旧衣回收预约分拣与公益去向公示平台

Vue 3 + Spring Boot 3 + PostgreSQL 一体化工程，覆盖「居民预约 → 回收员上门称重拍照 → 居民确认积分/捐赠 → 分拣中心五分类复核（含隐私衣物脱敏/拒收）→ 批次发运 → 公益机构签收 / 环保再生登记 → 公示端全流程透明 → 六类投诉跨角色协同 → 社区多维复盘」的完整闭环。

## 原始需求

> 建设社区旧衣回收预约分拣与公益去向公示平台，可采用 Vue 3、Spring Boot 和 PostgreSQL。居民提交旧衣回收预约时，平台记录衣物数量、品类、是否清洗、是否含鞋包被褥、上门地址、可预约时段和是否希望捐赠。回收员上门后进行称重、拍照、初步分类，并让居民确认积分或公益捐赠选项。分拣中心收到包裹后，按照可直接捐赠、需消毒整理、环保再生、不可回收和特殊处理进行复核，记录分拣员、重量差异、污损原因和去向。若居民质疑称重、上门迟到、衣物被误判不可捐赠、公益机构拒收、积分未到账或公示去向不透明，平台要把居民、回收员、分拣中心、社区、公益机构和积分财务放在同一回收单中处理。公示端展示批次去向、捐赠照片、公益机构签收和再生处理量，社区可以按小区、回收员、公益项目和投诉类型复盘回收效果。平台还要支持企业公益合作、学校捐衣活动、低收入家庭定向领取和环保积分兑换。对于带有校服、工作服或个人信息的衣物，分拣中心需要单独脱敏或拒收，避免公益流转中产生隐私风险。

## 一键启动（宿主 Docker Compose）

前置：宿主已安装 Docker 与 Docker Compose 插件。无需在本地安装 JDK / Maven / Node / PostgreSQL——全部由镜像内多阶段构建完成。

```bash
cp .env.example .env        # 可按需修改 CC_PUBLISH_PORT
docker compose up -d --build
```

- 仅 **web（nginx）服务** 发布到宿主机：`${CC_PUBLISH_PORT}:80`（默认 3089）；
- PostgreSQL 与 Spring Boot 后端**不发布宿主端口**，仅在 compose 内部网络通过服务名 `db` / `backend` 互访；
- 首次启动后端会自动建表并灌入演示数据（约需 60–90 秒，含镜像内 Maven 构建）。

查看健康状态与实际端口：

```bash
docker compose ps
docker compose port web 80        # 输出形如 0.0.0.0:3089
curl -s http://localhost:3089/api/public/health
```

浏览器访问：

- 公示端（免登录）：`http://<宿主IP>:3089/#/public`
- 业务端登录：`http://<宿主IP>:3089/#/login`

在容器/远程环境中可用 `http://host.docker.internal:<映射端口>` 访问。

停止并清理：

```bash
docker compose down              # 保留数据卷
docker compose down -v           # 同时删除数据库与上传照片卷
```

## 推荐业务游走路径

1. `resident` 登录 → 提交一件预约（可选学校/企业活动）；
2. `collector` 登录 → 抢单 → 上门登记（称重、上传照片、初步分类、迟到标记）；
3. `resident` → 在回收单点「确认积分/捐赠」，选择积分/捐赠/混合，积分实时入账；
4. `sorter` → 分拣复核：选择五分类、记录重量差异与污损原因；勾选「隐私风险」体验**脱敏后流转 / 拒收**；
5. `sorter` → 勾选已分拣单建立捐赠批或再生批 → 上传捐赠照片 → 发运；
6. `org` → 对在途捐赠批「验收签收」（上传签收照片）或「拒收并留证」（必选尺码/季节/卫生/其他类型 + 原因 + 复核照片）；再生批由 `sorter` 登记再生处理量；
7. 拒收后 `sorter` 在批次页「重新分拣处置」：逐单确定改配公益或转环保再生（记录新分类、重量变化、复核照片），再「建立再分配批次」（自动关联来源拒收批）；转再生批的公示说明会写明清拒收原因、处理机构与重量变化；
8. `community` → 合作与帮扶中登记脱敏的低收入家庭，从已签收批次「定向发放」；
9. `resident` → 对任一单发起投诉（六种类型）；依次用回收员/分拣/社区/财务登录在**同一投诉时间线**中协同，`finance` 可补发积分并结案；
10. `resident` → 用积分在商城兑换，也可在回收单详情开启「公示匿名」；`finance` → 确认发放、查看全量流水；
11. `community` → 社区复盘页按小区 / 回收员 / 公益项目 / 投诉类型切换图表；
12. 退出到 `/#/public` 公示端：批次去向、捐赠照片、机构签收照片与签收人、**拒收→重新分拣→替代去向流向链（含转再生的原因/机构/重量变化）**、再生处理量、五分类重量分布全部公开可查；选择匿名的住户仅显示批次与去向。

## 技术结构

```
.
├── docker-compose.yml      # db(PostgreSQL16) + backend(Spring Boot 3.3/JDK17) + web(nginx/Vue3)
├── .env.example            # CC_PUBLISH_PORT / 数据库 / JWT 密钥
├── backend/                # 多阶段 Dockerfile（Maven 构建 → JRE 运行，非 root + HEALTHCHECK）
│   └── src/main/java/com/clothing/recycle/
│       ├── model/          # 12 个实体与枚举（回收单为主线）
│       ├── repo/ service/  # JPA 仓库、事务化业务状态机与积分账本
│       ├── security/       # JWT + Spring Security 角色鉴权
│       ├── controller/     # 认证/回收单/批次/投诉/积分/合作帮扶/公示/复盘
│       └── seed/           # 启动演示数据 + 占位照片生成
└── frontend/               # Vite + Vue3 + Element Plus + Pinia + ECharts（nginx 多阶段构建）
```

关键设计：

- **同一回收单串联六角色**：`recycle_orders` 关联上门记录、分拣复核、批次、投诉与积分流水，投诉单以时间线（`complaint_events`）汇聚居民、回收员、分拣中心、社区、公益机构、积分财务各方处置；
- **积分账本**：`points_ledger` 采用带余额快照的流水表，获取/兑换/补发/活动奖励四类变动不可变留痕；
- **上门留证强制**：上门登记必须同时具备有效称重重量、初步分类与现场称重照片，缺一返回 4xx，单据保持「待上门」且不产生上门记录，为称重争议保留现场证据；
- **隐私衣物处置闭环**：分拣复核对校服、工作服、含个人信息衣物强制选择「脱敏后流转」或「拒收」——无处置结论、缺书面说明一律拒绝落库；脱敏流转必须上传**脱敏处理后复检照片**，且仅限可捐赠/消毒整理类；拒收单在状态层与入批校验双重拦截，无法进入任何批次、机构签收、公示溯源或低收入家庭定向领取；
- **同一份隐私结论对外**：批次、公示溯源、投诉处理统一展示标准化结论（`privacyConclusion`：标签/结论措辞/脱敏证据照片）；公示端不回传含姓名、校徽、登记号等原始个人标识的备注字段；居民还可对任一回收单开启**公示匿名**，公示端该衣物仅以「匿名住户」占位，只展示批次与去向；低收入家庭姓名电话仅脱敏存储；
- **机构拒收处置闭环**：拒收必须同时提供原因类型（尺码/季节/卫生/其他）、书面原因与现场复核照片，否则 4xx 且批次保持在途；拒收批次作为证据保留，回收单进入「待重分」。分拣中心逐单重新分拣（新分类、重量变化、逐单结论与复核照片），可选**改配其他公益机构/项目**或**转环保再生**；再分配批次关联来源拒收批，形成 拒收证据→重新分拣→替代去向 的完整流向链。转再生时公示必须说明拒收原因、处理机构与重量变化（如 3.15kg→3.00kg），并在再生登记后追加处置证明，避免居民误以为捐赠失败；
- **低收入家庭定向领取闭环**：社区凭低保证明/特困证明/临时救助材料/社区授权核验登记，记录需求人数、性别年龄、尺码、季节、衣物类型、是否接受二手、鞋包被褥需求、配送/自提与公示隐藏意愿。分拣中心**仅从公益机构已签收的「可直接捐赠」批**按尺码/季节/卫生/需求匹配（待消毒、环保再生、不可回收均不可发），属地小区/街道优先；企业/学校指定对象按指定匹配，但不跳过消毒、分拣与签收。领取时核验身份、与登记人关系，**代领须登记代领人及登记人电话确认/社区授权**，留存签收照片或签字，防止冒领与重复领取。尺码不合/需求不符/卫生质疑/临时放弃/物资不足/冒领等异常挂在**同一回收单**的协同时间线，只能换货/退回重新分拣/转其他家庭/补充分拣，**不得直接改写公示去向**。公示端仅展示批次、公益项目、发放户数/件数、完成状态与机构签收照片，不展示姓名、住址、身份证、联系方式、困难细节与领取人照片；要求隐藏的家庭统一显示"定向发放完毕"和批次编号。同一发放批次的**公益价值由财务只记一次**，居民已选积分的来源单不重复计捐赠金额；社区回访穿着情况、满意度与后续需求，进入公益项目账本与小区复盘（按项目汇总发放户数、件数、代领次数、平均满意度、后续需求）；
- **定向发放库存按件锁定（防跨家庭超额发放）**：来源回收单记录**可分配 / 已预占 / 已发放**三件数（`aid_allocatable_quantity` / `aid_reserved_quantity` / `aid_distributed_quantity`，可直接捐赠复核通过时按件入池）。匹配时对来源单逐单 `SELECT ... FOR UPDATE` 加锁并**按剩余可分配预占**，生成 `aid_distribution_items` 发放明细；计划件数超过剩余可分配直接 4xx，不产生任务、不改库存与公示。签收按同一明细把预占结转为已发放（实领超过任务预占 4xx，未领部分自动释放）；取消、转其他家庭释放未领预占；退回重新分拣/补充分拣释放预占并按明细扣减已发放（衣物退出可分配池、批次公示累计同步减少）；换货释放旧任务预占并对替代来源单重新预占。**公示发放数与公益价值只统计真实已发放件数**（发放明细已签收合计），记账件数超过批次实发数一律 4xx。来源单剩余可分配为 0 后自动退出匹配候选；并发匹配同一来源单时行级锁串行化，总预占不超过剩余量；
- **公示数据全部来自业务留痕**：批次照片、签收人、再生处理量由对应角色在流程中产生，无需另行编辑。

## 验证方式（= 宿主 docker compose up）

本工程的验收标准即：宿主机执行 `docker compose up -d --build` 后三个容器全部健康，且上述业务流可在浏览器与接口走通（详见上方端口与账号）。
